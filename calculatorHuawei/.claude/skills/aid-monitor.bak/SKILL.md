# AID Monitor Skill

## 概述

在当前对话会话结束前，Agent 回顾自身在本次对话中的所有操作，
识别错误和失败尝试，将错误分类并提取为可复用的领域知识模式。

**核心原则**：主要数据来源是当前对话的上下文记忆（Agent 自省），
产物和 git 历史作为补充确认。

## 前置条件

- 当前对话中发生了代码相关操作（编码、构建、测试、调试等）
- Agent 仍在同一对话会话中（上下文可用）

## 执行步骤

### 步骤 1：会话自省（上下文收集）

Agent 回顾当前对话的完整上下文，收集以下信息：

**1a. 会话元信息：**
- 本次对话的目标/任务是什么？
- 是否执行了 aid-workflow？如是，关联到哪个 `specs/changes/{session}/` 目录？
- 对话持续了多长时间？涉及哪些文件？

**1b. 操作回顾：**
- 执行了哪些操作？（代码生成、构建、测试、调试、设计等）
- 哪些操作一次成功？
- 哪些操作失败了？失败了几次？每次失败的原因是什么？
- 用户纠正了哪些错误？用户的纠正内容是什么？
- Agent 自己发现并修正了哪些错误？

**1c. 补充数据：**
- 读取相关产物（apply-report.md、tasks.md 等，如有）
- 检查 git 历史（本次会话时间范围内的提交）
- 读取已有的 `specs/guidelines/` 了解已知模式

### 步骤 2：Git 历史分析

分析本次对话时间范围内的 git 提交：

1. 确定时间范围（对话开始到当前时间）
2. 检查以下信号：
   - **revert 提交**：Agent 撤销了自己的代码
   - **fix-on-fix 模式**：连续多次修复同一问题
   - **重复尝试**：同一文件被多次修改（>3次）
   - **编译/构建失败后的修复提交**：commit message 中包含 fix、修复等关键词

### 步骤 3：错误检测（自动）

结合对话上下文和补充数据，识别错误：

**从对话记忆中提取：**
- Agent 生成了错误代码后被用户纠正
- Agent 执行构建/测试失败后需要修复
- Agent 做出了错误假设（关于 API、平台行为、项目结构等）
- Agent 重复尝试同一操作多次才成功
- Agent 跳过了应该执行的步骤
- Agent 的设计/方案被用户否决

**从产物中提取（如有）：**
- apply-report.md 中的 TDD 失败记录
- tasks.md 中标记为失败或重做的任务
- todo.md 中被取消或反复切换状态的步骤

**从 git 历史提取：**
- 步骤 2 中识别的所有信号

### 步骤 4：错误检测（用户标记）

向用户询问：

```
## 用户补充

自动检测到 {N} 个错误。

{列出检测到的错误摘要}

在本次对话中，是否有其他您观察到但未被自动检测的错误？
- 如有，请描述错误情况（发生了什么、正确做法是什么）
- 如无，输入"无"继续
```

### 步骤 5：错误分类

对每个检测到的错误，使用错误分类体系（参考 `references/error-taxonomy.md`）进行分类：

1. 确定主分类（CG/AD/WP/ET/DK/TS/UD）
2. 确定严重度（high/medium/low）
3. 分析根因（为什么 Agent 会犯这个错误？缺少什么知识？）
4. 判断是否可泛化为通用模式（该错误是否可能在其他会话中重复出现？）
5. 如果可泛化，提取模式描述

**分类结果需要用户确认后再继续。**

### 步骤 6：事件报告生成

使用 `templates/incident-report-template.md` 模板生成报告：

- **aid-workflow 会话**：存入 `specs/changes/{session}/incident-report.md`
- **自由会话**：存入 `specs/guidelines/incidents/{description}-{YYYYMMDD}.md`

### 步骤 7：知识库同步

#### 7a：推送到集中知识库

对每个可泛化的新模式：
1. 确定所属域（arkts/workflow/toolchain/...）
2. 检查集中知识库中是否已有相似模式
   - 如有：更新频次计数
   - 如无：分配新 ID，添加新条目
3. 写入 `skills/monitoring/knowledge-base/{domain}.md`

**模式 ID 规则**：`{分类代码}-{三位序号}`，如 `CG-001`、`DK-003`

#### 7b：拉取到本地指南

1. 确定当前项目的主要域（从对话上下文推断，或询问用户）
2. 从集中知识库中筛选该域的所有模式
3. 生成/更新 `specs/guidelines/{domain}.md`（使用 `templates/guideline-template.md` 格式）

## 产出物

| 产出物 | 路径 | 条件 |
|--------|------|------|
| 事件报告（workflow） | `specs/changes/{session}/incident-report.md` | 本次对话执行了 aid-workflow |
| 事件报告（自由会话） | `specs/guidelines/incidents/{description}-{YYYYMMDD}.md` | 本次对话未执行 aid-workflow |
| 集中知识库更新 | `skills/monitoring/knowledge-base/{domain}.md` | 有可泛化的新模式 |
| 本地指南更新 | `specs/guidelines/{domain}.md` | 始终刷新 |

## 约束

1. **不修改原有产物**：只新增 `incident-report.md`，不修改已有文件
2. **不删除知识库条目**：只允许新增条目或更新已有条目的频次
3. **格式一致性**：所有知识库条目必须严格遵循条目模板格式
4. **无错误时不生成报告**：如果未检测到任何错误，告知用户并跳过报告生成，但仍执行步骤 7b（拉取指南）
5. **用户确认**：分类结果需要用户确认后再写入知识库
6. **自省诚实**：Agent 必须诚实地报告自己的错误，不得隐瞒或淡化失败
