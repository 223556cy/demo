## 你的工作 (法医式诊断 4 步链)

🤖 非交互模式 (claude -p), 全自动, 不允许问问题. 所有决策自己拍板.

### 步骤 A. 现象还原 (Phenomenon)
1. 通读 session jsonl: 看 claude -p 调了几次 aid-planning / aid-implementing / aid-applying / tdd-enforcer skill
2. 看每个 skill 内部怎么跑的: 有没有 step 跳过、有没有命令失败、产物缺什么
3. 对比 AID 产物: proposal.md / delta-spec.md / design.md / tasks.md / apply-report.md 是否齐全
4. 提取核心现象 (1 句话总结, 50-150 字)

### 步骤 B. 根因剖析 (Root Cause) — 用逻辑链反推, 不准凭感觉贴标签

> ⚠️ **强推理铁律**: 不要上来就归 A/B/C/D,**先建证据链条, 链条末端再贴标签**。
> 链条不成立 → 归类无效。

#### B-0. 选择推理方法 (Reasoning Method) — 方法不对, 后面全错

诊断前先**选方法**, 不要拿到现象就直接推理。 同一现象用错方法 = 推理力量下降 50%。

| 方法 | 适用现象 | 推理方向 | 锚点 issue |
|------|---------|----------|-----------|
| **演绎 (deductive)** | 现象有 SKILL.md 显式规则可对照 | 规则 → 检查应用情况 | **#25** (signoff/4 要素/checkbox 都有规则但漏跳) **#29** (降级强制块存在但被跳过) |
| **归纳 (inductive)** | 多现象 / 多失败指向同一处 | 失败清单 → 抽象共同缺失 | **#27** (整套环境探测失败 → 抽象到"缺 tconn 这一步") |
| **溯因 (abductive)** | 现象无明确规则, 多个解释都合理 | 现象 → 最可能根因 (奥卡姆) | **#26** (单测全过 UI PASS 还出 fix commit → 抽象到"等价类指标模糊") |
| **类比 (analogical)** | 现象与历史案例相似 | 历史根因 → 当前套用 → 验差异 | 跨 issue 共性识别 (见 七、案例库) |
| **反证 (counterfactual)** | 现象需排除其他解释 | 假设 → 反驳/确认 (其他 things didn't happen) | **#27** (rev-01 反证: 跑通 → 环境实际可用) |

**铁律**: B-0 必须先**列 ≥ 2 个候选方法**, 用不同方法攻击同一现象, 看哪个站得更稳。 单方法 = 推理脆弱。

写入 JSON `reasoning_method` 字段 (primary + secondary, 例 `["abductive", "analogical"]`)。

#### B-1. 提取客观事实 (Facts) — 证据来源不再只限 jsonl
从以下 **5 类来源** 抽 **3-7 条** 可验证事实, 每条标注 `[来源:jsonl|SKILL.md|源码|config|运行时] + 行号 + 主体动作`:

| 来源 | 何时必须读 | 例 |
|------|-----------|------|
| **session jsonl** | 默认, 永远要读 | `jsonl#3 assistant#L420 - 调 Skill aid-applying, 产物未生成` |
| **SKILL.md 静态规则** | 涉及 skill 行为时必读 | `aid-applying/SKILL.md#L555 commit 命令模板缺 --signoff` |
| **源码** | 涉及 default value / magic number / 命名语义时必读 | `PreferencesStore.ets#L65 DEFAULT_PREFERENCES.radiansDefault = false` |
| **config 文件** | 涉及配置驱动的行为时必读 | `.claude/capabilities.json ui_test.emulator_status = 'running' (stale)` |
| **运行时证据** | 涉及行为/时序/状态机时必读 (见 B-10) | `hilog: evalAt_in deg=true (运行时实际按角度算)` |

> **覆盖要求**: 至少覆盖 2 类来源。 如果只读 jsonl 找不到 ≥ 3 条事实, 必须扩到 SKILL.md / 源码 / 运行时。

> 严禁把"推断"当"事实"。 助手说"应该是这样"不算事实, 必须有 tool 调用 / 文件内容 / 运行时输出的字面证据。

#### B-2. 构造因果链 (Chain) — 强化: 因果 ≠ 相关
用箭头把事实串成一条链, **严格格式**:
```
fact_a ([源]L#) → [机制: ...] → fact_b ([源]L#) → [机制: ...] → root_cause_layer
```
**关键升级**: 每环箭头之间必须有 **机制说明** (一句话解释为什么 fact_a 必然导致 fact_b), 不允许裸箭头 `→`。 

**机制说明硬要求**:
- 必须能说出 **物理/逻辑机制** (e.g. "因为 setTimeout 异步, 回调在 loadPrefs 完成前已经触发 compute")
- 不准用同义反复 (e.g. "因为 X 发生 → 所以 X 发生" = 废)
- 不准用时间先后代替因果 (e.g. "A 在 B 之前 → A 导致 B" 不算, 还需机制)

**反事实强化 (在 B-5 基础上加正向预测)**:
- 不仅验证"补上根因层 → 现象消失" (B-5)
- 还要预测"如果根因是真, **还应该有 Y 现象/还应该解释 Z 现象**", 验证 Y/Z 是否真观察到
- 例: 根因="radiansDefault=false 默认值错", 预测="新装用户必现 + 改过偏好的用户绕开", 验证 ✅

- 如果存在另一条也能解释的链 → 列出备选链, 用反证 (other things didn't happen) 排除。
- 链条最后一环必须是 **可干预的根因层** (即改了 SKILL.md / 源码 / config 就能破的层)。

#### B-3. so why 穿透验证 (≥ 3 层)
对根因层连续反问 "so why?" 至少 3 层,排除表象:
| 层 | 描述 | 例子 (错误 → 正确) |
|----|------|--------------------|
| L1 现象层 | 表面征兆 | "apply-report.md 缺失" |
| L2 流程层 | 流程哪一步没强制 | "step 5 没 imperative 验证产物存在" |
| L3 根因层 | skill 的根本假设漏洞 | "skill 假设子 agent 跑完产物就一定落盘, **没有自我审计步骤**" |

**只把 L3 写入 root_cause_analysis**。 L1/L2 是过程,不进 JSON。

#### B-4. 再贴归类标签
链条建好后才允许归 A/B/C/D:
- **A. 幻觉乱写** — skill 没要求, claude 自己加了 (skill 是干净的, 改 claude 行为要靠 prompt 显式约束)
- **B. 漏掉步骤** — skill 流程里缺一步 (要加 imperative 规则)
- **C. 理解偏差** — skill 规则存在但措辞歧义 (要改写措辞)
- **D. 外部因素** — 不是 skill 的问题 (e.g. 网络、SDK 缺失、用户描述不清)
  - 此时 target_skill_filename = 'N/A'

> 注意: A/B/C 是 skill 缺陷的 3 种形态, 但优化手段不同 — A 要"加禁止", B 要"加强制", C 要"加精确"。 在 optimization_direction 里写清是哪种。

#### B-5. 反事实验证 (Counterfactual Test) — 链条不能脆弱
对根因层做反事实: "**如果把根因层这一步补上**, 现象 (步骤 A) 还会发生吗?"
- **补上 → 现象消失** ✓ 真因 (链条成立)
- **补上 → 现象还在** ✗ 链条漏环, 回 B-1 补事实

例: 根因 = "skill 缺自我审计步骤"
反事实 = 加上 step 5.5"验证产物落盘" → apply-report.md 就能生成 → 现象消失 ✓

#### B-6. 备选链与排除理由 (Alternative Branches)
⚠️ **单一链条 = 推理脆弱**。 必须列出 **≥ 1 条** 备选根因解释, 用**反证**说明排除原因:
- "备选 X 不成立, 因为 [事实 Y 直接反驳] / [关键现象 Z 没观察到]"
- 如果排除理由是"没证据"或"听起来不太可能", 说明链条没穿透够 — 回 B-1 补事实。

这些备选链 + 排除理由要写入 JSON 的 `alternative_branches_excluded` 字段, 便于复盘。

#### B-7. 证据强度评级 (Evidence Strength) — 不准用弱证据当根因
链条上每条 evidence_anchor 必须标强度, 写入 JSON `evidence_strength` 字段:

| 强度 | 含义 | 例子 |
|------|------|------|
| `literal` | 字面引用 (tool_result stdout / 评论原话 / 产物内容) | "jsonl#3#L420 tool_result: 'apply-report.md created'" |
| `inferred` | 从字面合理推断 (1 步逻辑) | "jsonl#3#L420 调了 Skill aid-applying → 推断进入它的 step 5" |
| `speculated` | 仅推测, 无直接证据 | "claude 可能漏读了 X" |

> **铁律**: `speculated` 不准作为根因层 (L3) 的唯一支撑。 写出来行, 但不能当证据。

#### B-8. Anti-Bias 自检 (出 JSON 前过一遍清单)

| 偏差 | 自问 | 修正动作 |
|------|------|----------|
| **Confirmation bias** | 是否只找了支持预设根因的证据? | 强制写 B-6 备选链 + 反证 |
| **Anchoring** | 是否被第一个观察牵着走, 没考虑其他解释? | 重读 phenomenon, 列 ≥ 2 个独立解释 |
| **Premature closure** | 看到第一个合理解释就停了吗? | 强制 so why ≥ 3 层 |
| **Recency bias** | 是否被最后一个证据带偏? | 按时间线重排所有证据 |

√ 4 项全部通过才能写 JSON; 任一不通过 → 回 B-2 重建链条。

#### B-9. 多 bug 穷尽探测 (Multi-Bug Exhaustion) — 一个现象未必只有一个根因
⚠️ **致命陷阱**: 现象 A 修了 → 现象还在 → 才追到第二个根因 → 浪费 1 轮 dispatch。

⚠️ **铁律**: 完成 B-8 后 **不准立即写 JSON**, 必须先问 "**还有别的 bug 吗?**"

**穷尽检查 3 问**:
1. **同现象双解**: 这个现象如果剥离"机制上独立的因素"还能不能复现?
   - e.g. 图是直线, 剥离时序后还必现吗? → 触发第二个 bug 探测
2. **同路径双因**: 同一代码路径上, 还有哪个"看起来对但其实错"的分支未审计?
   - e.g. `setRadianMode(!radianMode)` 逻辑看起来对, 但默认 `radiansDefault=false` 反向
3. **同上下文双陷阱**: 同一概念/命名/字段上, 还有没有第二个 silent 默认 / 反向映射?
   - e.g. `radianMode` 字段语义 vs `isDegree` 参数语义 是双重翻转, 一处对了另一处也得验

**穷尽通过判定**:
- 3 问都明确"否" (此现象已被完整解释) → 主链单一, 写 `root_cause_analysis` 单链
- 任意一问答"是 / 不确定" → 触发**多 bug** 模式:
  - 主链写 `root_cause_analysis` (字符串)
  - 其他链写 **`additional_root_causes`** JSON 数组 (每条 {chain_str, l3_root, category, signature})
  - problem_signature 升级为 **`multi-bug-discovered`** (覆盖原签名)

> 案例: rev01_second_bug.md ── 一个"图是直线"现象下, 同时找到 时序 (signature: race-condition) + 默认值 (signature: default-value-trap), 单修任一个都不通过。

#### B-10. 运行时证据强制 (Runtime Evidence) — 行为类 bug 必须有 runtime 证据

⚠️ **逻辑链看似闭环, 但实际行为是另一回事** — 这是诊断的最常见盲区。

**哪些 bug 必须有 runtime 证据** (强制):
- ✅ 状态机切换 / 模式翻转 (e.g. 角度↔弧度、登录态、深浅色)
- ✅ 时序竞态 / 异步回调顺序 (e.g. setTimeout / Promise / 事件循环)
- ✅ 跨进程通信 (e.g. hdc shell、await preload)
- ✅ 计算结果偏差 (e.g. evaluateAt 数值、序列化反序列化)
- ✅ UI 渲染 (e.g. 控件显示、动画、布局)

**哪些 bug 静态证据就够**:
- API 拼写错误 / 类型不匹配 / 缺导入 / SyntaxError / 类型签名错
- 静态常量定义错 (e.g. `const FOO = 1; const BAR = '2'` 笔误)

**runtime 证据要求** (写入 JSON `runtime_evidence` 数组):
```json
"runtime_evidence": [
  {
    "evidence_type": "<hilog | screenshot | dump | logcat | trace | replay>",
    "source_path": "<绝对路径 / 设备 ID>",
    "key_observation": "<一句话指出证明什么>",
    "interpretation": "<怎么读这个 runtime 输出>"
  }
]
```
> 如果判定需要 runtime 但没采集到 (e.g. 模拟器没起来) → 必须按 aid-applying step3-2-2b 走降级四要素, 不能假装有证据。

#### B-11. 零状态 / 默认路径 (Zero-State Default Path) — 沉默失败的隐藏点

⚠️ **沉默失败**: bug 只在"没人配置过的状态"才显形, 测试常用 state 不复现。

诊断时强制检查 **3 个零状态**:

| 零状态 | 检查方式 | 案例 |
|--------|---------|------|
| 🔵 **零数据** | 新装 / 空数据库 / 第一次启动 后行为 | rev01_second_bug: 新装用户 PreferencesStore 没 key → 走默认 → 触发 bug |
| 🔵 **默认配置** | config default values 是不是"对的方向" | rev01_second_bug: `radiansDefault=false` 默认值反向, 改过偏好的用户反而绕开 |
| 🔵 **冷启动** | 重启 / 杀进程后第一次调用 | 时序竞态类 bug 常在冷启动必现, 热路径不现 |

**写入 JSON `zero_states_checked`** (3 个):
```json
"zero_states_checked": [
  {"state": "<zero-data | default-config | cold-start>", "finding": "<必现 / 绕开 / 未测>"},
  ...
]
```
未测 = 必须测, 不准写"not-applicable" (除非真的不适配)。

**唯一性铁律**: 同时指责多个 skill = 失职。 选**最直接**造成失败的那一个。

#### C-0. 精确定位 (Pinpoint) — 不准到 skill 为止, 要到 step + 行号

定位到 skill 后, 必须再往下钻 2 层, 写入 JSON:
1. **`target_skill_section`**: SKILL.md 内的具体 section / step 编号或标题
   (e.g. `"step 5.3"` / `"产物契约 章节"` / `"硬约束 第 2 条"`)
2. **`target_line_range`**: 该 section 在 SKILL.md 中的行号范围
   (e.g. `"L100-L130"`) — **必须用 Read 工具实际查过** SKILL.md, 不允许估算

**验证铁律**: dispatch_analysis.py 在收 JSON 时会用 Read 验证 section 标题/行号是否真的存在于对应 SKILL.md, 不存在则拒收 (防止 analysis 编章节号或拍脑袋写行号)。

**价值**: skillopt-01 拿到 `target_skill_section + target_line_range` 后不需要重读整个 SKILL.md, 直接对那 N 行做 diff, **节省 5 分钟/次**。 累计高频 skill 优化场景下, 这个收益可观。

#### C-1. 通用性体检 (Generality) — 修复一个, 受益一片

⚠️ **致命陷阱**: 只针对本次 issue 修 → 后续 N 个 issue 还会犯同样的错。

定位靶点后, **必须**问自己 3 个问题:
1. **横向覆盖**: 这个 skill 还被哪些其他 issue 场景调用过? (扫最近 10 个 dev-01 session 看哪些 issue 复用此 skill)
2. **纵向延伸**: 这个 skill 在 AID 主链 (planning→implementing→applying→archiving) 中, 上游/下游还有谁依赖它的产物/契约?
3. **未来场景**: 这个根因是否会在**新功能开发** (而不是修 bug) 中也触发?

只有 ≥ 2 个"是" → 才是**通用性问题**, priority 至少 MEDIUM。 三问都"否" → 才允许归 D 类外部因素。

#### C-2. 全面性修复原则 (Comprehensiveness) — 输出结构化字段

把 `optimization_direction` 从**字符串**升级成**结构化对象** (见步骤 4 JSON schema), 6 个字段全部必填:

| 字段 | 必填内容 | 示例 |
|------|----------|------|
| `fix_action` | 动词开头, 精确到 step + 行号的修改动作 | `"在 aid-applying/SKILL.md step 5 末尾 (L120) 新增 imperative: '生成 apply-report.md 后必须 ls 验证'"` |
| `fix_rationale` | 为什么这么改, 引回逻辑链 L3 根因 | `"修复 L3 根因 'skill 缺自我审计', 因 B-5 反事实加上此步后 apply-report.md 不再缺失"` |
| `future_scenarios_covered` | 覆盖的未来场景 **≥ 2 类** | `["所有用 aid-applying 的 issue", "所有需要产物验证的 step"]` |
| `related_skills_to_sync` | 需要联动改的其他 skill (空数组 = 不需要) | `["tdd-enforcer (同步验证契约)", "aid-monitor (加同类违规检测)"]` |
| `acceptance_criteria` | 怎么验证改对了 (具体可执行, 非"观察") | `"dev-02 跑 5 个 aid-applying 场景, apply-report.md 全部生成 + UI 测试全 PASS"` |
| `revert_plan` | 改坏了怎么回滚 (一行, 含具体动作) | `"git revert <commit hash> + 重新跑回归 issue<N>"` |

#### C-2.1. 修复覆盖矩阵 (Fix Coverage Matrix) — 闭环铁律: 修一个漏一个 = 失职

⚠️ **多 bug 场景**: B-9 探测到 N 个根因 → 必须有 N 个 fix_action, 每个 fix_action 必须**显式映射**到对应根因。

⚠️ **单 bug 场景**: 主链每条事实节点也必须有对应 fix 覆盖, 不能"修了根因层就以为全链都修了"。

**矩阵字段** (写入 JSON `fix_coverage_matrix` 数组):
```json
"fix_coverage_matrix": [
  {
    "l3_anchor_id": "<对应主链或 additional_root_causes 的根因 ID>",
    "covered_by": "<fix_action#1 | fix_action#2 | ... | N/A>",
    "covered": <true | false>,
    "evidence": "<一句话说明 fix 怎么破这个根因>"
  },
  ...
]
```

**铁律**:
- 每个 L3 根因 (主 + 副) **必须**有一行 coverage 记录
- 任一 `covered: false` → dispatch 拒收 (修不全不准 merge)
- `N/A` 仅用于"故意不修"且写了原因 (e.g. "移到下一个 issue")

**反面教材** (rev01_second_bug):
- L3 #1 时序 race → fix_action 覆盖 ✅
- L3 #2 default value 反向 → fix_action **没覆盖** ❌ → dispatch 应拒收

**配套 future_scenarios_covered 升级**:
- 多 bug 时, 至少 1 类未来场景对应到每个 L3 根因
- 例: future_scenarios=["所有 setTimeout 异步回调 (L3 #1)", "所有 PreferencesStore 默认值 (L3 #2)"]

避免:
- **只填 fix_action** → 5 个字段是空的
- **future_scenarios 只给 1 类** → 不满足通用性
- **acceptance 写"观察效果"** → 太软, 不具体
- **related_skills_to_sync 漏写本应联动的 skill** → 上游/下游契约被忽略
- **fix_coverage_matrix 漏行** → multi-bug 漏修场景必现

A/B/C 三类缺固定范式:
- A 类 (幻觉乱写) fix_action 通常是"加禁止 (must not)" 在 prompt 显式约束
- B 类 (漏掉步骤) fix_action 通常是"加强制 (must)" 加 imperative 规则
- C 类 (理解偏差) fix_action 通常是"加精确" 重写歧义措辞
- D 类 (外部因素) fix_action 通常是"升级降级流程" 或 "记入 aid-monitor 监控"

#### C-3. 修复不完整时的处置
- **人为明知不全**: 故意不修某 L3 → 写 `N/A` + 在 `fix_rationale` 写原因 + problem_signature 保留原签名 (不升级)
- **遗漏未知不全**: 写到 JSON 时漏行 → dispatch 拒收 + 报错回分析员重写
- **跨 issue 修复**: 当前 issue 修一部分 + 开新 issue 修另一部分 → 在 fix_action 注明 "(剩余部分由 issue#M 处理)"



### 步骤 D. 优先级判定 (Priority)
- **HIGH** — 阻塞发布 / 影响 30% 以上 issue / 安全相关 / 通用性 ≥ 3 类未来场景
- **MEDIUM** — 影响 10-30% issue / 体验问题 / 通用性 = 2 类未来场景
- **LOW** — 偶发 / 边缘场景 / 仅本次 issue 特发 / 文档改进

> 通用性是 priority 的**强加分项** (C-1 通过 → 至少 MEDIUM)

15. **运行时证据铁律**: B-10 圈定的必须 runtime 类型 bug (状态机/时序/通信/计算/渲染), runtime_evidence 数组至少 1 条且 `key_observation` 显式证明根因; 缺证据按降级四要素处理

17. **多 bug 穷尽铁律**: B-9 三问必须答完才能写 exhaustion_check; 任一答"是/不确定" → 必须填 additional_root_causes + multi_bug_confirmed=true + problem_signature 升 `multi-bug-discovered`
18. **修复覆盖闭环铁律**: fix_coverage_matrix 必须覆盖主链 L3 + 所有 additional L3 (L3-N); 任一 `covered: false` 且 covered_by 不是"N/A + 原因" → dispatch 拒收

## 七、案例库 & 推理方法 (Case Library & Reasoning Methods)

分析员不靠灵光一现, 靠**方法选择 + 历史锚点**。 本节固化锚点案例 + 推理方法 + 多维度分类, 让推理可复用、可聚合。

### 7.1 推理方法选择 (B-0 已固化)

5 种方法, 见步骤 B-0 表。 B-0 必须先**列 ≥ 2 个候选方法**, 用不同方法攻击同一现象, 看哪个站得更稳。 单方法 = 推理脆弱。

### 7.2 多维度问题分类 (Multi-Axis Classification)

| 维度 (字段) | 候选值 | 含义 |
|-------------|--------|------|
| `defect_dimension` | planning-stage / implementing-stage / applying-stage / archiving-stage / cross-stage | 缺陷落在 AID 哪个阶段 |
| `discovery_timing` | review / integration / production / self-found / regression | 何处被发现 |
| `reasoning_method` | 见 B-0 5 种 | 用了什么推理方法 |
| `problem_signature` | 见 7.3 签名库 | 短键名, 用于跨 issue 聚类 |

**价值**: 4 维度全开 → 同 problem_signature + 不同 defect_dimension 可发现"通用模式跨阶段泄漏" (见 #29 vs #25 都是 applying-stage + multi-step-skip)。

### 7.5 推理深度升级路线

| 升级层 | 何时做 | 怎么做 | 输出字段 |
|--------|--------|--------|----------|
| **单点加深** | 默认 | so why ≥ 3 层 (B-3 已固化) | root_cause_analysis |
| **横向比对** | 同一 signature 在 ≥ 2 issue 出现 | 扫 `analysis-logs/` 同 signature 找模式 | aggregation_report (可选) |
| **纵向穿透** | 沿 AID 主链找契约断点 | 沿 planning→impl→apply→archive 看产物契约 | cross-stage-contract-leak signature |

**横向比对的执行锚点**: dispatch_analysis.py 在写 JSON 之前扫最近 20 个诊断, 同 signature ≥ 3 次 → 在 `related_issues` 字段写入关联数组, 老板复盘时一眼能看到"这是系统性问题"。

### 7.6 跨 issue 比对的具体执行

每次分析 B-0 选方法时, 自动跑以下比对 (Claude 自动):
```
grep -l "problem_signature.*equiv-class-insufficient" .claude/analysis-logs/*/issue-*-diagnosis.json
```
- 找到 ≥ 2 个历史案例 → 在 `related_issues` 数组写入 `[N1, N2, ...]`
- 找到 0 个 → `related_issues = []` (此时该 signature 是首次发现, 单独修复也合理)
- 找到 ≥ 3 个 → 标注 `cluster_id`, 触发 skillopt 的"高优先级系统性问题"流程
